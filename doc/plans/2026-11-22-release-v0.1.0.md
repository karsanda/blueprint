# Release v0.1.0: Blueprint for Ubuntu and macOS — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The MVP can be installed on Ubuntu (`.deb`) and macOS (`.dmg`, Apple Silicon), works there as on Linux from source, and a `v*` tag builds both into a draft GitHub release.

**Architecture:**
- **Main process:**
  - reads the login shell's environment when started from the desktop;
  - detaches itself when started from a terminal;
  - on macOS, gets a standard menu, login shells and a `ps`-based busy-shell check.
- **Renderer, on macOS:** Option acts as Alt, and Blueprint itself pastes on Ctrl+Shift+V.
- **Packaging and CI:**
  - electron-builder packages `out/`;
  - CI runs both suites on macOS too;
  - `release.yml` builds both packages, on a PR as a dry run and on a tag into a draft release.

**Tech Stack:** As in build step 8 (Electron 45.4.1, electron-vite 6.0.0, node-pty 1.1.0, React 19, TypeScript 7, Vitest 5, @playwright/test 1.65), plus electron-builder 26.18.0 (new dev dependency, pinned).

**Spec:**
- Notes: [Release](../../entries/domain/release/notes.md) (the approved design, with the `blueprint` command refined to a self-detaching app); [Workspace](../../entries/domain/workspace/notes.md) and [Claude sessions](../../entries/domain/claude_sessions/notes.md) for what exists.
- The use cases stay platform-neutral: their test cases must pass on macOS CI too.

## Global Constraints

- **App identity:** name `Blueprint`, app id `io.github.karsanda.blueprint`. The version comes from `package.json` (`0.1.0`) and the tag is `v0.1.0`.
- **Targets:** Ubuntu `.deb` for amd64 only, macOS `.dmg` for arm64 only. No Developer ID signing and no notarization; electron-builder's ad-hoc signature on macOS.
- node-pty is unpacked from the asar archive (`asarUnpack` covering `node_modules/node-pty/**`).
- **Loading the login-shell environment:**
  - It runs only when `TERM` is absent from Blueprint's environment, on both platforms, before any program starts.
  - The run is `$SHELL -i -l -c` printing `env` between two markers, with a 5000 ms limit.
  - Blueprint takes the login shell's `PATH`, and every other variable its own environment lacks.
  - On failure or timeout it changes nothing.
- **Detaching:**
  - It happens only when the app is packaged, standard input is a TTY, and `BLUEPRINT_DETACHED` is unset.
  - The second start gets `BLUEPRINT_DETACHED=1`, `detached: true`, `stdio: 'ignore'`, and its folder argument made absolute.
  - The first process then exits with code 0.
- **User data:**
  - A packaged app uses Electron's default for the name `Blueprint`.
  - An unpackaged run whose app name is `blueprint` (`pnpm dev`) uses `<appData>/blueprint-dev`.
  - Runs named `Electron` (e2e and hands-on) are unchanged.
- **macOS menu:**
  - **Blueprint:** `about`, separator, `hide`, `hideOthers`, `unhide`, separator, `quit`.
  - **Edit:** `undo`, `redo`, separator, `cut`, `copy`, `paste`, `selectAll`.
  - **Window:** `minimize`, `zoom`, separator, `front`.

  Everything uses Electron roles. On Linux, `Menu.setApplicationMenu(null)` as today.
- **macOS terminals:**
  - xterm's `macOptionIsMeta: true`;
  - Ctrl+Shift+V pastes the clipboard through `term.paste` exactly once (Chromium does not paste on it there);
  - shells start with the argument `-l`.
- **Busy shell on macOS:**
  - one `ps -A -o pid=,pgid=,tpgid=,comm=`, through `execFile`, with a 2000 ms limit;
  - the foreground group is the shell's `tpgid`. There is none when it is the shell's pid or 0 or less;
  - otherwise the program is the lowest pid with `pgid` equal to that group, named by `basename(comm)`;
  - errors give `null`.

  Linux keeps `/proc`. `TerminalManager.foreground` becomes `Promise<string | null>` on both platforms.
- **The macOS `blueprint` script:** `build/bin/blueprint`, copied to `Contents/Resources/bin/blueprint` and executable. It runs `"$(dirname "$(realpath "$0")")/../../MacOS/Blueprint" "$@"`.
- **Release workflow:**
  - `.github/workflows/release.yml` runs on tags `v*`, and on pull requests that change the packaging files, as a build-only dry run;
  - it fails when the tag is not `v` and `package.json`'s version;
  - it only ever creates a **draft** release, with text from `doc/releases/<tag>.md`;
  - permissions are `contents: write` only for the release job.
- **Tests:**
  - The e2e harness sets `TERM=xterm-256color` unless a test asks otherwise, so the login-shell run is skipped.
  - Chromium's headless flags are passed only on Linux.
  - A Linux-only test is skipped on macOS with a stated reason.
- No production test-only branches beyond the e2e probe.
- Commit messages follow the repo's style, with no attribution lines.
- **Before finishing:** `sh scripts/check_links_integrity.sh` prints only `check-done`; `pnpm typecheck && pnpm lint && pnpm format:check && pnpm test && pnpm e2e` passes locally; CI passes on Ubuntu and macOS.
- Pushing `release/v0.1.0` to run macOS CI is part of this plan. Tagging `v0.1.0` and publishing the draft are not: they wait for the Developer.

## Review Focus

1. **A login shell that is slow, noisy or broken at startup** (oh-my-zsh banners, a p10k instant prompt, an `exit 1` in `.zshrc`). Blueprint starts within about 5 seconds, its environment is never replaced by junk, and it never hangs. Test: Task 1.
2. **`blueprint ~/x`, then the terminal is closed.** Blueprint and its Claude sessions keep running, and the prompt came back at once. Test: Task 2 (unit) and Task 8 (hands-on).
3. **A busy shell or a pipeline on macOS.** Closing it still asks first, through `ps`. Test: Task 4 (unit), plus `shells.spec.ts` and `manager.test.ts` on macOS CI.
4. **Paste on macOS.** Cmd+V and Ctrl+Shift+V each paste exactly once. Ctrl+Shift+V on Linux still pastes once, not twice. Tests: Task 3, and `keys.spec.ts` on both platforms.
5. **The release workflow.** A pull request run builds but never creates a release. A tag that does not match the version fails before building. Nothing is ever published without the Developer. Test: Task 7 (dry run on the PR, and a reading of the workflow).

### Task 1: Read the login shell's environment when started from the desktop

**Files:**
- Create: `src/main/environment.ts`, `src/main/environment.test.ts`, `tests/e2e/environment.spec.ts`
- Modify: `src/main/index.ts`, `tests/e2e/launch.ts`, `tests/e2e/fixtures/fake-term.mjs`

**Interfaces:**
- Produces:
  - `needsLoginEnvironment(env: NodeJS.ProcessEnv): boolean`, which is true when `TERM` is absent or empty.
  - `parseMarkedEnv(output: string, marker: string): Record<string, string> | null`. It reads the `KEY=VALUE` lines between the two markers, and gives `null` without both markers.
  - `mergeEnvironment(current: NodeJS.ProcessEnv, login: Record<string, string>): NodeJS.ProcessEnv`. It takes the login `PATH`, adds the variables `current` lacks, and keeps every other current value.
  - `loginEnvironment(shell: string, run?: Runner): Promise<Record<string, string> | null>`. `Runner` wraps `execFile` with a 5000 ms timeout, and any failure gives `null`.
- Produces, in `index.ts`: before `resolveFolder`, when `needsLoginEnvironment(process.env)`, merge the result into `process.env`.
- Produces, in the tests:
  - `LaunchOptions.env?: Record<string, string | undefined>` overrides the launch environment, where `undefined` removes a variable;
  - `launch` sets `TERM: 'xterm-256color'` by default;
  - the fake program's `start` record gains `env: { BLUEPRINT_LOGIN_MARK, PATH }`.

- [ ] **Step 1: Write the failing tests.**
  - `environment.test.ts`:
    - `'a desktop start reads the login shell, a terminal start does not'`: `needsLoginEnvironment({})` and `({ TERM: '' })` are true, and `({ TERM: 'xterm' })` is false;
    - `'only what lies between the markers counts'`: banner lines and a p10k escape before the first marker, and a prompt after the second, are ignored. A value holding `=` keeps it, and a missing second marker gives `null`;
    - `'the login PATH replaces the current one, and only missing variables are added'`;
    - `'a shell that fails or runs too long changes nothing'`: a `Runner` that rejects, or times out, gives `null`.
  - `environment.spec.ts`, `'Claude Code gets the login shell's environment when Blueprint starts from the desktop'`:
    - launch with `env: { TERM: undefined }`, `shell: '/bin/sh'` and a `HOME` whose `.profile` exports `BLUEPRINT_LOGIN_MARK=yes` and prepends `$HOME/extra` to `PATH`;
    - `claude.start`'s `env.BLUEPRINT_LOGIN_MARK` is `'yes'`, and its `PATH` starts with `<home>/extra`.

    A second test, `'a start from a terminal skips the login shell'`, uses the default `TERM` and expects no mark.
- [ ] **Step 2: Run them.** Run: `pnpm test src/main/environment && pnpm build && pnpm exec playwright test tests/e2e/environment.spec.ts`. Expected: FAIL.
- [ ] **Step 3: Implement.** The marker is a fresh random string per run.
- [ ] **Step 4: Run all checks.** Run: `pnpm typecheck && pnpm lint && pnpm format:check && pnpm test && pnpm e2e`. Expected: PASS.
- [ ] **Step 5: Commit.** `git commit -m "Give programs the login shell's environment when Blueprint starts from the desktop"`
